# Plan: Prioritized On-Device OCR Language Passes

## Summary

- Goal: reduce iOS OCR latency by avoiding the current fixed supplemental Vision loop over Japanese, Korean, Chinese, and English whenever one likely language can be inferred cheaply.
- Keep accuracy safe by ranking language passes instead of hard-selecting one language forever. If the first likely language still produces a weak/noisy title, continue through the remaining fallback languages.
- Treat Latin as an accessory signal, not a primary language signal. Suffixes like `ex`, `EX`, `GX`, `V`, `VMAX`, `VSTAR`, and short trainer tokens like `N` must not cause `en-US` to outrank Japanese/Korean/Chinese when East Asian script or joiners are present.
- Main target: [PokemonCardNameExtractor.swift](app/Modules/PokemonFeatures/Sources/PokemonOcr/PokemonCardNameExtractor.swift:31), where supplemental OCR currently performs up to 12 extra Vision requests.

## Key Changes

- Add a small pure Swift utility, likely `PokemonOcrLanguagePassPlanner`, in the `PokemonOcr` target.
- Expose an internal static API for tests via `@testable`:

```swift
enum PokemonOcrLanguagePassPlanner {
    static func supplementalLanguagePasses(
        for candidates: [PokemonOcrCandidate],
        selectedCandidate: PokemonOcrCandidate?
    ) -> [[String]]
}
```

- Return the same language groups already used today, only reordered by evidence:

```swift
["ja-JP"]
["ko-KR"]
["zh-Hans", "zh-Hant"]
["en-US"]
```

- Strong language signals:
  - `の`, Hiragana, or Katakana -> Japanese first.
  - `의` or Hangul -> Korean first.
  - `的` or Han/CJK-only text -> Chinese first, with Japanese still kept as fallback because Kanji/Han can be ambiguous.
  - Latin-only plausible titles -> English first.
- Latin handling:
  - Strip known mechanic suffixes before inference: `ex`, `EX`, `GX`, `V`, `VMAX`, `VSTAR`.
  - Ignore short Latin fragments when East Asian script exists, especially `N` in titles like `Nのゾロアーク`.
  - Only rank `en-US` first when there is no supported East Asian script/joiner evidence.

## Extractor Flow

- Keep the initial broad Vision pass unchanged: `recognitionLanguages: nil`.
- Keep existing candidate selection and `shouldRunSupplementalLanguagePass` behavior unchanged initially.
- When supplemental OCR is needed:
  - Compute `let languagePasses = PokemonOcrLanguagePassPlanner.supplementalLanguagePasses(for: candidates, selectedCandidate: selectedCandidate)`.
  - Replace the fixed `Self.supplementalLanguagePasses` loop with `languagePasses`.
  - For each language group, run the existing three recognitions unchanged:
    - full normalized image
    - enhanced title crop
    - enhanced focused crop
  - After each language group, immediately re-run `chooseBestCandidate`.
  - If `shouldRunSupplementalLanguagePass(for: selectedCandidate)` is now false, break early and skip the remaining language groups.
- Keep known-sample fallback as the final last resort only if all ranked supplemental passes still fail.
- Do not change `VisionPokemonTextRecognizer` defaults yet. The broad initial recognition remains useful as a cheap source of script evidence and preserves existing behavior.

  - `ホップのカビゴン` ranks Japanese first because of `の`.
  - `Nのゾロアーク` ranks Japanese first despite leading Latin `N`.
  - `이브이ex` ranks Korean first despite Latin suffix.
  - `音箱蟀ex` ranks Chinese first despite Latin suffix.

  - When the first ranked language remains noisy, the extractor continues to later fallback groups.

## Assumptions

- The implementation should optimize common latency without sacrificing correctness, so ranked fallback is preferred over hard language filtering.
- No new dependencies should be added. Script inference should use Unicode scalar ranges already present in `PokemonCardTitleNormalizer`.
- Keep the utility pure/static per repo Swift guidance; do not inject it as a dependency.
- Do not change OCR crop geometry, Vision recognition level, lexicon loading, or title normalization except where needed to share script/suffix helpers cleanly.
- Preserve Swift 6 warning-as-error compatibility and avoid type assertions/casts.
