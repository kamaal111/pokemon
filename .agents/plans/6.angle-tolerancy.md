# Tolerant Angled-Card Shape Detection Plan

## Summary

The current scanner is finding candidates but rejecting them as invalid because validation is still too rectangle/ratio strict. The next fix should stop treating a Pokemon card as a near-perfect upright `63 / 88` bounding box. Instead, it should accept angled, perspective-skewed card candidates using a score-based detector, keep the existing buffered rectangular crop behavior, and make every rejection explainable in logs/UI.

## Key Changes

- Replace hard aspect-ratio validation in `PokemonCardShapeDetector` with tolerant scoring:
  - Keep confidence and area thresholds, but make aspect ratio a soft score instead of a hard rejection.
  - Accept projected/bounding-box ratios across a wider range, roughly `0.45...1.05`, because angled cards can look wider/narrower than `63 / 88`.
  - Use a minimum final score threshold, not “must match target ratio within 25%.”
  - Keep rejecting obvious junk: tiny components, near-full-frame table regions, landscape-wide regions, and low-confidence noise.
- Preserve Vision rectangle detection but use more of its information:
  - Store `VNRectangleObservation` corners, not only `boundingBox`.
  - Add `normalizedCorners` to the internal detection/candidate model.
  - Compute metrics from both the bounding box and quadrilateral edges: area, bounding aspect, average side-length ratio, convexity, and confidence.
  - Relax `VNDetectRectanglesRequest` settings for handheld perspective, especially aspect range and quadrature tolerance.
- Improve fallback detection so it does not validate a projected perfect-ratio crop:
  - Score the raw foreground/color component first.
  - Use color/content contrast and component area as positive evidence.
  - Only expand to the Pokemon-card aspect ratio after a candidate is selected for cropping.
- Keep crop behavior rectangular for this pass:
  - Do not add deskew/perspective correction yet.
  - Crop from the accepted candidate’s bounding box or quadrilateral bounding box, expand to `63 / 88`, apply the existing buffer, clamp to image bounds, and return the existing `PokemonCardCropResult`.
- Make debugging actionable:
  - Add rejection reasons and metrics to `PokemonCardShapeDetectionCandidate`, such as `lowConfidence`, `tooSmall`, `tooLarge`, `poorScore`, `unlikelyOrientation`.
  - Log every throttled frame with each candidate’s source, confidence, score, bounding rect, aspect, area, and rejection reasons.
  - Update the UI feedback to show the best rejected candidate reason, for example: `Best rejected: score 0.48 < 0.55, aspect tolerated, area ok`.
  - Continue drawing all candidates: accepted candidates solid, rejected candidates dashed.

## Implementation Details

- In `PokemonCardShapeDetector`, introduce:
  - `PokemonCardShapeCandidateMetrics`
  - `PokemonCardShapeCandidateRejectionReason`
  - `PokemonCardShapeQuadrilateral`
  - `scoreCandidate(_:configuration:) -> PokemonCardShapeCandidateEvaluation`
- Default scoring recommendation:
  - `confidenceScore`: weight `0.30`
  - `areaScore`: weight `0.20`, ideal area roughly `0.10...0.45`
  - `aspectScore`: weight `0.20`, soft target `63 / 88`, tolerated range `0.45...1.05`
  - `contentScore`: weight `0.20`, from fallback/color mask overlap when available
  - `shapeScore`: weight `0.10`, based on quadrilateral convexity/side sanity
  - Accept candidates with total score around `0.55` or higher.
- Update `bestDetection` to rank all candidates by score and select the best accepted one.
- Update `PokemonCardAutoCaptureGate` stability:
  - Use center drift plus intersection-over-union.
  - Default: center drift `<= 0.06`, IoU `>= 0.65`, area drift `<= 0.25`.
  - Do not reset stability just because the source changes from Vision to fallback if the candidate overlaps the previous one.
- Keep performance constraints:
  - Detection remains throttled before frame snapshot.
  - Do not add OCR/text matching.
  - Do not run contour/edge fallback every frame unless Vision and the color fallback both fail or produce low scores.

## Test Plan

- Add detector validation tests:
  - Accept an upright card-like candidate near `63 / 88`.
  - Accept angled/perspective candidates with bounding aspect outside the old 25% limit.
  - Accept the screenshot-like case where candidates are visibly over the card but currently `valid=0`.
  - Reject tiny, near-full-frame, very low-confidence, and truly landscape/background candidates.
  - Pick the highest scoring candidate when Vision and fallback both produce candidates.
- Add scoring/rejection tests:
  - Candidate reports include score, metrics, and rejection reasons.
  - Best rejected candidate explains why it was not accepted.
  - Logs have enough fields to diagnose confidence, aspect, area, score, and reason.
- Add auto-capture gate tests:
  - Stable angled detections trigger after 3 frames.
  - Small perspective jitter does not reset stability.
  - Large movement still resets stability.
  - Source switching between overlapping Vision/fallback candidates does not reset stability.
- Run verification:
  - `just test-app` while iterating.
  - `just format-app`.
  - `just ready-app`.
  - `just ready` last, with any unrelated Node native-binding failure called out separately.

## Assumptions

- The scanner should accept handheld perspective and mild rotation, not require a perfect upright rectangle.
- The crop should remain a buffered rectangular crop, not a deskewed/perspective-corrected card image.
- This remains shape/color based only; no OCR, title extraction, or Pokemon text matching should be used for capture.
- The existing overlay/debug UI is part of the feature and should stay until live detection is reliable.
