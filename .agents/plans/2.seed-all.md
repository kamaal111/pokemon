# Implementation Plan: Seed all Pokemon species with configurable cooldown

## Goal

Update the existing Pokedex seed workflow so it:

1. seeds **all Pokemon species currently reported by PokeAPI at runtime**, not just the first 40
2. enforces a configurable cooldown from `.env` so a successful full sync can run at most once per configured interval
3. applies that cooldown **only after** a successful full sync or a confirmed already-current no-op
4. does **not** block retries after partial or failed runs

This plan is written as a full handoff for another agent. It includes the relevant codebase findings, the decisions already made, and the intended implementation sequence.

## User-confirmed requirements

- “All pokemons” means **all species currently reported by PokeAPI at runtime**, not a new hardcoded larger limit.
- The cooldown must be configurable via `.env`.
- The default desired cadence is effectively “once per day,” but the user wants the option to change it later, such as to 7 days.
- A failed or partial seed run must **not** start the cooldown window.
- The cooldown starts only after:
  - a successful full sync, or
  - a no-op run that confirms the local dataset is already current

## High-confidence conclusions from codebase research

### 1. The current implementation is hardcoded around `40`

Relevant files:

- `api/src/seed/constants.ts`
- `api/src/seed/pokeapi.ts`
- `api/src/seed/service.ts`
- `api/src/seed/repository.ts`
- `api/src/tests/fixtures.ts`
- `api/src/seed/service.test.ts`
- `api/src/seed/routes/seed-pokedex.test.ts`

Observed behavior:

- `api/src/seed/constants.ts` defines:
  - `POKEAPI_SPECIES_PAGE_SIZE = 20`
  - `POKEDEX_SEED_TARGET = 40`
- `api/src/seed/pokeapi.ts`:
  - builds list URLs with `offset` and `limit`
  - validates list/detail payloads with Zod
  - collects species summaries until `POKEDEX_SEED_TARGET - resumeOffset`
  - skips any species id above `40`
- `api/src/seed/service.ts`:
  - stops immediately when contiguous seeded prefix reaches `40`
  - fetches candidate summaries, filters existing ids, fetches details, then inserts each species
- `api/src/seed/repository.ts`:
  - computes contiguous prefix only inside `between(id, 1, POKEDEX_SEED_TARGET)`
- tests and fixtures are written around the same fixed limit

### 2. The current architecture is already good for this change

Relevant files:

- `api/src/seed/service.ts`
- `api/src/seed/config.ts`
- `api/src/seed/cli.ts`
- `api/src/seed/routes/seed-pokedex.ts`
- `justfile`

Observed behavior:

- both the CLI and HTTP route already delegate to the same core seed service
- the repository already exposes root commands:
  - `just seed-pokedex`
  - `just db-reseed-local`
  - `just db-generate`
  - `just db-check`
  - `just ready`
- this means the change should stay centered on the existing seed service and supporting seed/database modules rather than introducing a parallel entrypoint

### 3. The current schema stores per-row `seededAt`, but that is not sufficient for cadence gating

Relevant file:

- `api/src/db/schema/pokemon-species.ts`

Observed behavior:

- each species row stores `seededAt`
- there is **no** table or metadata record for “last successful full seed sync”
- there is **no** generic app settings or metadata table elsewhere in `api/src/db/schema/`

Why this matters:

- if a full rerun is already current and inserts `0` rows, there is no row timestamp to update
- if a partial run inserts some rows and then fails, row timestamps alone would not distinguish that failure from a completed sync
- therefore, the cooldown should not rely only on `pokemon_species.seeded_at`

Conclusion:

- a small persisted sync-state surface is likely required
- that may require a schema addition plus a Drizzle migration

### 4. Env configuration currently has no seed-specific cadence option

Relevant file:

- `api/src/env.ts`

Observed behavior:

- env parsing already uses Zod and defaults
- current env keys are `PORT`, `DEBUG`, `MODE`, `LOG_LEVEL`, `DATABASE_URL`, and `DATABASE_AUTH_TOKEN`
- there is no seed cadence variable yet

Conclusion:

- the cadence should be added through the existing Zod env parsing path
- `.env.example` should be updated so the new variable is discoverable

### 5. Test infrastructure already mocks PokeAPI and is the right place to make this dynamic

Relevant files:

- `api/src/tests/fixtures.ts`
- `api/src/seed/service.test.ts`
- `api/src/seed/routes/seed-pokedex.test.ts`

Observed behavior:

- the integration fixture builds deterministic list and detail responses
- the list mock currently:
  - uses `POKEAPI_SPECIES_PAGE_SIZE`
  - caps page generation with `POKEDEX_SEED_TARGET`
  - returns `count: 1302` but still stops pagination at the local hardcoded target
- this means tests currently simulate “the API says many exist, but local seed logic only wants 40”

Conclusion:

- fixture generation should become configurable by total mocked species count
- tests should assert dynamic all-species behavior against a smaller mocked total for speed and clarity, instead of inserting the live PokeAPI total during tests

## Recommended implementation design

## A. Replace the fixed seed target with a discovered upstream target

Implementation intent:

- stop using a fixed `POKEDEX_SEED_TARGET`
- use the species list metadata returned by PokeAPI to determine the current upstream total

Likely code changes:

- `api/src/seed/constants.ts`
  - keep `POKEAPI_SPECIES_PAGE_SIZE`
  - remove or stop using `POKEDEX_SEED_TARGET`
- `api/src/seed/pokeapi.ts`
  - add a helper that fetches and validates the first list page and returns:
    - `count`
    - `next`
    - `results`
  - update summary collection so it can:
    - start from `resumeOffset`
    - continue paging until it has collected all needed summaries after the resume point
    - ignore ids at or below the resume point
    - deduplicate ids
    - stop based on the discovered upstream total rather than `40`

Important detail:

- the existing list schema already validates `count`, `next`, `previous`, and `results`
- the current code already derives ids from the species URL, which should be preserved

## B. Keep resume logic, but make it work across the full upstream range

Implementation intent:

- preserve the current contiguous-prefix approach because it supports resumable seeding
- remove the artificial `1..40` ceiling from the repository logic

Likely code changes:

- `api/src/seed/repository.ts`
  - update `getContiguousSeededPrefix()` so it no longer queries only `between(1, target)`
  - likely select all existing species ids ordered ascending and stop on the first gap from `1`

Notes:

- for the current scale of PokeAPI species, a simple ordered id query is probably acceptable
- do not rewrite the core idempotent insertion behavior unless necessary; it already checks for existing parent rows inside a transaction before inserting parent and child rows

## C. Introduce a configurable cooldown backed by persistent sync state

Implementation intent:

- enforce a cooldown between successful full syncs
- do not enforce the cooldown after partial or failed runs
- allow the interval to be configured from `.env`

Likely code changes:

- `api/src/env.ts`
  - add a validated variable for the cooldown interval
  - the most likely shape is an integer number of days
- `.env.example`
  - document the new variable
- `api/src/seed/config.ts`
  - thread the parsed cooldown config into the seed dependency/config surface
  - consider also injecting a `now()` dependency so time-based behavior is testable without brittle clock mocking

Recommended env design:

- prefer a name that is explicit and feature-scoped, such as `POKEDEX_SEED_COOLDOWN_DAYS`
- parse it with `z.coerce.number().int().positive()` and give it a sensible default aligned with the user’s current expectation

## D. Persist “last successful full sync” separately from species data

Implementation intent:

- store a timestamp for the last successful full sync or already-current no-op
- use that timestamp to decide whether the cooldown is still active

Why this is needed:

- a no-op current-state check must still be able to start the cooldown
- a partial failure must not look like a successful sync

Preferred persistence direction:

- add a small metadata surface rather than overloading species rows
- because no metadata table currently exists, this may require:
  - a new Drizzle schema entry under `api/src/db/schema/`
  - a generated migration in `api/drizzle/`

Reasonable design options:

1. a tiny feature-scoped sync-state table for the Pokedex seed workflow
2. a generic application metadata table if the repository already seems likely to need reusable key/value metadata soon

Given the current codebase:

- there is no existing generic metadata table
- the narrowest change may be a small dedicated sync-state table
- if the implementing agent prefers a generic metadata table, it should still stay minimal and clearly justified

Required behavior for this persisted state:

- write/update it only after:
  - a successful full sync, or
  - a no-op confirmation that local data is already current relative to upstream
- do not update it on:
  - upstream fetch failures
  - validation failures
  - partial insert failures

## E. Service-level flow after the change

Target behavior for `seedPokedex()`:

1. determine the current upstream species total
2. read the last successful sync state
3. if the cooldown has not expired, return a no-op style result before heavy seeding work
4. compute the current contiguous seeded prefix
5. if the local dataset is already current relative to the upstream total:
   - update the persisted successful-sync timestamp
   - return `{ saved: 0 }`
6. collect all missing candidate summaries after the contiguous prefix up to the upstream total
7. filter out already stored noncontiguous ids
8. fetch and normalize only missing species details
9. insert each species transactionally as today
10. if the run reaches a successful full current state, update the persisted successful-sync timestamp
11. return the number of newly saved species

Important nuance:

- the implementing agent should be careful about the order of the cooldown check versus the already-current check
- the user requirement says the cooldown should apply only after a successful full sync or confirmed current-state no-op
- therefore, the service needs enough information to distinguish:
  - “blocked by cooldown after recent success”
  - “already current and now marking the success timestamp”
  - “not current, so proceed even if a prior failed attempt happened recently”

## F. Tests to update or add

### Existing tests that will need revision

- `api/src/seed/service.test.ts`
- `api/src/seed/routes/seed-pokedex.test.ts`
- `api/src/tests/fixtures.ts`

### Test updates expected

1. replace fixed `40` assertions with a configurable mocked total
2. keep coverage for:
   - first run from empty database
   - rerun against fully seeded data
   - resume from a contiguous prefix
   - skipping already-present noncontiguous ids
   - upstream listing failures
3. add coverage for cooldown behavior:
   - a successful full sync starts the cooldown
   - a confirmed already-current no-op starts or refreshes the cooldown timestamp
   - a second run inside the cooldown does not reseed
   - a run after the cooldown expires is allowed
   - a failed run does not start the cooldown

### Test implementation guidance

- prefer fixture configurability over massive test datasets
- inject time into the seed service if possible so cadence tests can avoid brittle global date mocking
- keep using the existing mocked fetch path rather than real network requests

## Risks and pitfalls to avoid

- Do not infer success from `pokemon_species.seeded_at` alone.
- Do not start the cooldown after a failed or partial run.
- Do not keep tests tied to the live PokeAPI total; keep them deterministic and smaller.
- Do not introduce a separate seed path for CLI and HTTP; both must keep delegating to the same service.
- Do not bypass env validation; add the cadence variable through the existing Zod schema.
