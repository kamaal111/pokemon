# PokemonOcrScreen Vision OCR POC With Image-Backed Evaluation Tests

## Summary

Implement the on-device OCR POC inside the existing `PokemonOcr` feature module by replacing the stubbed `PokemonOcrScreen` with a sample-image workflow backed by Apple Vision. The design will make the OCR pipeline easy to test by separating pure logic from Vision/UIImage glue, and it will add declarative Swift tests that validate both normalization/scoring behavior and end-to-end extraction against the real sample card images already present in `samples`.

## Key Changes

- Extend `app/Modules/PokemonFeatures/Sources/PokemonOcr` with a small, testable OCR domain:
  - `PokemonCardNameExtractor`
  - `PokemonCardNameExtractionResult`
  - `PokemonOcrCandidate`
  - `PokemonCardTitleNormalizer`
  - `PokemonCardNameCandidateSelector`
  - `PokemonCardTitleCropper`
  - `UIImage` normalization/cropping helpers kept thin
- Keep orchestration in `PokemonCardNameExtractor`, but move decision-heavy logic into pure helpers so tests can be mostly data-driven:
  - crop-rect calculation from image size and ratios
  - OCR candidate normalization
  - candidate filtering/scoring/selection
  - final title normalization
- Introduce a tiny OCR engine abstraction so the extractor is easy to test without depending on Vision in every case:
  - `protocol PokemonTextRecognizing`
  - production implementation wraps `VNRecognizeTextRequest`
  - tests can inject a fake recognizer for deterministic candidate-selection scenarios
- Use a tunable crop configuration instead of hardcoding ratios inline:
  - default `xMin = 0.12`, `xMax = 0.75`
  - default `yMin = 0.02`, `yMax = 0.13`
  - cropper returns both the `CGRect` and cropped `UIImage` for debug/test visibility
- Configure Vision for the POC exactly as requested:
  - `VNRecognizeTextRequest`
  - `.fast`
  - `usesLanguageCorrection = false`
  - `recognitionLanguages = ["ja-JP", "ko-KR", "en-US"]`
  - initial `minimumTextHeight = 0.05`
- Candidate selection stays simple but explicit:
  - reject empty/junk candidates
  - reject obvious non-name fragments like `HP`, `기본`, `진화`, `進化`, `から`, `테라스탈`
  - prefer candidates with supported scripts or valid Latin suffixes
  - reward confidence and reasonable length
  - keep both raw and normalized text for UI debugging
- Normalization stays conservative:
  - trim and collapse whitespace/newlines
  - width-fold full-width Latin characters
  - remove internal whitespace for Japanese/Korean titles
  - preserve valid modifiers like `ex`, `EX`, `GX`, `V`, `VMAX`, `VSTAR`
  - repair trailing single `e` after Japanese/Korean/CJK scripts to `ex`
- Replace `PokemonOcrScreen` stub with a simple `@State`-driven UI:
  - picker for sample images
  - original image preview
  - title-crop preview
  - `Run OCR` button
  - loading/error state
  - selected candidate display
  - normalized extracted title
  - raw candidate list with confidence
- Package the sample images into the Swift package resources for this feature while sourcing them from the existing repo fixtures under `samples/`:
  - copy or reference the chosen fixtures into `PokemonFeatures` resources during implementation
  - start with the real samples already available: `eevee.jpg`, `shiny-charmeleon.jpg`, `trainers-snorlax.jpg`
  - optionally include `trainers-wold.jpg` if the title-joiner case remains in scope for the simple top-region crop
- Update `app/Modules/PokemonFeatures/Package.swift`:
  - add resources to the target
  - add a test target
  - use Swift Testing style for app tests

## Test Plan

- Add Swift Testing suites using `@Suite` and backtick test names, matching repo conventions.
- Make the tests strongly declarative and table-driven wherever possible:
  - normalization cases stored as input/expected arrays
  - candidate-selection cases stored as candidate fixtures plus expected winner
  - sample-image extraction cases stored as sample-name plus expected extracted title
- Pure logic tests:
  - `"이브이e"` -> `"이브이ex"`
  - `"이브이 e"` -> `"이브이ex"`
  - `"ホップ の カビゴン"` -> `"ホップのカビゴン"`
  - `"ピカチュウｅ"` -> `"ピカチュウex"`
  - `"リザード"` -> `"リザード"`
  - ignored fragments are filtered out
  - high-confidence supported-script candidates beat junk candidates
  - valid suffix forms are preserved instead of over-normalized
- Cropper tests:
  - relative crop rect matches expected pixel bounds for a known image size
  - crop rect stays within bounds
  - orientation-normalized crop path returns a non-empty image
- Extractor tests with fake recognizer:
  - extractor returns the expected selected candidate and normalized title for deterministic OCR outputs
  - extractor surfaces useful errors for missing crop / no candidates
- End-to-end evaluation tests with real sample images and real Vision OCR:
  - load sample fixtures from package test resources
  - run the actual extractor on-device
  - assert the final normalized title matches expected values for the supported fixtures
  - start with a small stable set: `eevee.jpg`, `shiny-charmeleon.jpg`, `trainers-snorlax.jpg`
- Test structure should make it easy to expand later with more fixtures and expectations, not bespoke one-off tests.
- Validation after implementation:
  - `just test-app`
  - `just ready-app`
  - `just ready`

## Assumptions

- `PokemonOcrScreen` remains the only screen for this flow; no duplicate screen will be introduced.
- The feature currently does not have an established view-model layer, so the POC UI will use local `@State` unless exploration during implementation reveals a stronger existing pattern inside the app target.
- The existing repo sample images under `samples` are the source of truth for the first evaluation fixtures.
- This POC still excludes camera capture, card rectangle detection, SQLite name matching, networking, and alternate OCR strategies.
- Because Vision OCR can have some variance, the image-backed end-to-end tests will target a curated subset of fixtures that are stable with the chosen crop and normalization rules, while most behavioral coverage stays in pure deterministic tests.
