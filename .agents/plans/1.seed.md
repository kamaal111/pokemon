# Implement SQLite PokeAPI seed workflow

## Problem

Add a repeatable seeding workflow that fetches the first 40 Pokemon species from PokeAPI, persists them in SQLite without duplicating already-seeded entries, and makes the workflow invocable from `just`. The stored shape should preserve the data demonstrated in `scratch.1.json`, `scratch.2.json`, and `scratch.3.json`, while being organized for efficient API-side reads later.

## Current state

- Root `justfile` exposes project, quality, and API recipes, but nothing for data seeding.
- `scratch.js` shows the source-of-truth fetch pattern for species detail records and writes the same fields that should be persisted.
- The API already has a `/seed/pokedex` route stub behind `MODE=SEED`, but it currently returns `{ saved: 0 }` and there is no database layer yet.
- The repo does not currently include SQLite integration or a persistence module for Pokemon data.
- Existing relevant files:
  - `justfile`
  - `api/package.json`
  - `api/src/seed/index.ts`
  - `api/src/seed/router.ts`
  - `api/src/seed/routes/seed-pokedex.ts`
  - `api/src/env.ts`

## Required source API behavior

- Discovery starts from `https://pokeapi.co/api/v2/pokemon-species`.
- The listing response is paginated with `count`, `next`, `previous`, and `results`.
- Each page returns up to 20 species summaries shaped like:
  - `name`
  - `url`
- To get the first 40 species, follow pagination twice:
  1. `https://pokeapi.co/api/v2/pokemon-species`
  2. `https://pokeapi.co/api/v2/pokemon-species?offset=20&limit=20`
- Each summary `url` points at a species detail record such as `https://pokeapi.co/api/v2/pokemon-species/1/`.

## Required persisted payload shape

The user wants the stored data to match the fields gathered by the existing scratch workflow. Each species detail record currently keeps:

- `id`
- `name`
- `evolution_chain.url`
- `color.name`
- `color.url`
- `evolves_from_species` as nullable `{ name, url }`
- `generation.name`
- `generation.url`
- `habitat` as nullable `{ name, url }`
- `is_baby`
- `is_legendary`
- `is_mythical`
- `names[]` entries shaped as:
  - `name`
  - `language.name`
  - `language.url`
- `genera[]` entries shaped as:
  - `genus`
  - `language.name`
  - `language.url`
- `pokedex_numbers[]` entries shaped as:
  - `entry_number`
  - `pokedex.name`
  - `pokedex.url`

Representative examples already observed during analysis:

- Bulbasaur (`id=1`) has `evolves_from_species = null`, `color.name = green`, `generation.name = generation-i`, `habitat.name = grassland`, and multilingual `names`, `genera`, and `pokedex_numbers`.
- Ivysaur (`id=2`) has `evolves_from_species.name = bulbasaur`.
- Venusaur (`id=3`) has `evolves_from_species.name = ivysaur`.

## Proposed approach

1. Add a shared seed service in the API package that:
   - checks the already-seeded contiguous species range starting from id `1`,
   - derives the initial pagination offset from that contiguous range,
   - walks the paginated `pokemon-species` listing from that offset until 40 species are collected,
   - fetches each species detail payload,
   - maps the needed fields from the scratch examples,
   - writes them to SQLite with insert-only semantics so each species is only stored once.
2. Design the SQLite schema around API retrieval:
   - a primary `pokemon_species` table for one-row-per-species fields,
   - child tables for multilingual names, genera, and pokedex numbers,
   - indexes on species id/name and child foreign-key lookup columns.
3. Expose the seeding flow through a dedicated executable script and a `just` recipe.
4. Reuse the same shared service from the existing seed route so CLI-triggered and API-triggered seeding stay consistent.
5. Add focused tests around normalization/idempotency and update dependency/config wiring as needed.
6. Do not stop at “implementation complete” until the verification checklist below has been executed and the final handoff explains what was verified.

## Confirmed scope

- The first implementation should seed only the first 40 species so the stored output can be reviewed easily.
- “Only filled in once” means the seed operation must be safe to rerun without creating duplicate parent or child records.
- The implementation stops at the seed workflow plus a retrieval-friendly schema. No new API read endpoint is included in this scope.

## Proposed schema

### `pokemon_species`

One row per species with columns similar to:

- `id INTEGER PRIMARY KEY`
- `name TEXT NOT NULL UNIQUE`
- `evolution_chain_url TEXT NOT NULL`
- `color_name TEXT NOT NULL`
- `color_url TEXT NOT NULL`
- `evolves_from_species_name TEXT NULL`
- `evolves_from_species_url TEXT NULL`
- `generation_name TEXT NOT NULL`
- `generation_url TEXT NOT NULL`
- `habitat_name TEXT NULL`
- `habitat_url TEXT NULL`
- `is_baby INTEGER NOT NULL`
- `is_legendary INTEGER NOT NULL`
- `is_mythical INTEGER NOT NULL`
- `seeded_at TEXT NOT NULL`

Indexes:

- unique/primary key on `id`
- unique index on `name`

### `pokemon_species_names`

One row per localized name:

- `pokemon_species_id INTEGER NOT NULL`
- `language_name TEXT NOT NULL`
- `language_url TEXT NOT NULL`
- `name TEXT NOT NULL`
- unique key on `(pokemon_species_id, language_name)`

### `pokemon_species_genera`

One row per localized genus:

- `pokemon_species_id INTEGER NOT NULL`
- `language_name TEXT NOT NULL`
- `language_url TEXT NOT NULL`
- `genus TEXT NOT NULL`
- unique key on `(pokemon_species_id, language_name)`

### `pokemon_species_pokedex_numbers`

One row per pokedex mapping:

- `pokemon_species_id INTEGER NOT NULL`
- `pokedex_name TEXT NOT NULL`
- `pokedex_url TEXT NOT NULL`
- `entry_number INTEGER NOT NULL`
- unique key on `(pokemon_species_id, pokedex_name)`

Idempotency strategy:

- parent rows use `INSERT ... ON CONFLICT(id) DO NOTHING`
- child rows use composite unique constraints plus `INSERT ... ON CONFLICT DO NOTHING`
- each seed run is safe to execute repeatedly without duplicate rows or rewriting existing species
- writes should run in transactions so a species is either fully stored or not stored at all

## Resume, deduplication, and fetch-once guarantees

The implementation should make duplicate work impossible at three layers:

1. **Resume from the stored contiguous range**
   - Read the already-seeded ids for the current target window and determine the longest contiguous range starting at `1`.
   - Example:
     - if ids `1..18` exist and `19` is missing, resume from offset `18`
     - if ids `1..40` already exist, return early with nothing to fetch
   - For the user’s example, if the first 40 ids are already stored, the same resume rule would start later work from offset `40`, which means listing begins at species `41`.
   - For the current scope, because the target is capped at 40 species, a contiguous range of `1..40` means the seed command becomes a no-op.

2. **Paginated discovery dedupe**
   - Extract the numeric species id from each listing `url`.
   - Keep an in-memory `seenIds` set while traversing pages.
   - Begin the first listing request at the computed offset, e.g. `?offset=<resumeOffset>&limit=20`.
   - Stop only after collecting enough **unique** ids to fill the target window through species `40`.
   - Never enqueue the same species id twice even if a later page unexpectedly repeats it.

3. **Skip already-seeded species before detail fetch**
   - After collecting candidate ids, query SQLite once for existing ids as a safety check, for example:
     - `SELECT id FROM pokemon_species WHERE id IN (...)`
   - Build a `missingIds` list from the candidate ids minus the existing ids.
   - Fetch species detail payloads **only** for `missingIds`.
   - This ensures rerunning the seed command does not re-fetch already-stored species, even if the stored ids are not perfectly contiguous.

4. **Write-once persistence**
   - Insert the parent `pokemon_species` row first with `ON CONFLICT(id) DO NOTHING`.
   - Only insert child rows for species ids that were newly inserted in the current transaction.
   - Child tables also use composite unique constraints with `DO NOTHING`.
   - Result: the same species id is never written twice, and an existing species does not get updated during later runs.

## Notes

- The existing `scratch.js` currently fetches individual species by id; the planned seed service should preserve its selected fields but switch to paginated discovery for the first 40 species.
- A normalized schema is the safest default because names, genera, and pokedex numbers are one-to-many and likely query targets for later API work.
- The plan should remain self-contained because later execution context may not include the scratch files or this conversation history.
- To honor “ever only filled in once,” the seed flow should prefer **skip existing ids** over update-in-place behavior.
- The resume offset should come from the longest contiguous seeded range so a fully seeded prefix can be skipped before any pagination or detail fetch work starts.

## Verification requirements

The execution agent must not stop when the code merely looks correct. The task is only complete after the agent has high confidence that the implementation works as expected, and the final response must explain exactly what was done to verify that.

### Post-change verification checklist

Use a fresh SQLite database for verification so the results are deterministic.

1. **Seed from an empty database**
   - Run the new `just` seed recipe once.
   - Verify the command succeeds.
   - Verify `pokemon_species` contains exactly 40 rows.
   - Verify the stored ids are exactly `1..40`.

2. **Verify representative stored values**
   - Confirm `pokemon_species` contains:
     - `id=1`, `name=bulbasaur`, `color_name=green`, `generation_name=generation-i`, `habitat_name=grassland`
     - `id=2`, `evolves_from_species_name=bulbasaur`
     - `id=3`, `evolves_from_species_name=ivysaur`
   - Confirm child tables contain related rows for:
     - localized names
     - localized genera
     - pokedex numbers

3. **Verify rerun safety**
   - Run the same `just` seed recipe a second time against the same database.
   - Verify the second run does not increase the row count in `pokemon_species`.
   - Verify the second run does not increase child table counts unexpectedly.
   - Verify the second run proves no new species were fetched or inserted for the current 40-item window.

4. **Verify duplicate protection with SQL**
   - Run duplicate-detection queries that must return zero rows for:
     - duplicate `id` values in `pokemon_species`
     - duplicate `(pokemon_species_id, language_name)` pairs in `pokemon_species_names`
     - duplicate `(pokemon_species_id, language_name)` pairs in `pokemon_species_genera`
     - duplicate `(pokemon_species_id, pokedex_name)` pairs in `pokemon_species_pokedex_numbers`

5. **Verify resume-offset behavior**
   - With ids `1..40` already stored, run the seed command again.
   - Verify the command exits early for the current capped scope, or otherwise proves it skipped all already-seeded ids before attempting detail fetches.
   - If the implementation exposes the computed offset in logs or output, verify that it resolves to `40`.

6. **Verify integration quality**
   - Run the relevant API tests for the new modules and route behavior.
   - Run the repo verification recipe again after implementation:
     - `just ready-api`

### Final handoff requirements

The execution agent’s final response must explicitly state:

- which commands were run
- which database assertions were checked
- what proved the second run was a no-op
- whether any failures were found during verification and how they were resolved
