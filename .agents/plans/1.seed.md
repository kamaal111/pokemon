# Pokedex seed workflow

## Purpose

This plan is the single source of truth for regenerating the Pokedex seed feature.

It describes the feature in a way that should still make sense if a future agent
reimplements it in a different language, framework, ORM, database library, or project
layout. The goal is to preserve the behavior, data model, constraints, and validation
expectations rather than any one implementation's file structure.

## Feature goal

Add a repeatable workflow that seeds the first 40 Pokemon species from PokeAPI into the
application database.

The workflow must:

- fetch the first 40 species from PokeAPI through paginated species discovery
- normalize the fetched data into a retrieval-friendly relational shape
- avoid duplicating previously seeded data
- be safe to rerun
- support both programmatic and command-line execution
- support database reset and reseed workflows for local development
- fail clearly when upstream dependencies fail

## Final behavior

The completed feature includes:

- a seed operation targeting exactly the first 40 Pokemon species
- paginated discovery from the public PokeAPI species endpoint
- strict validation of external API responses before persistence
- normalized persistence for parent species rows plus one-to-many child records
- idempotent rerun behavior
- resume behavior based on the longest contiguous seeded prefix
- a route or equivalent trigger for HTTP-based execution
- a CLI or equivalent command for direct execution
- automated tests covering success, rerun safety, resume behavior, and upstream failure
- local database reset and reseed tooling

## Source API behavior

Discovery starts from:

- `https://pokeapi.co/api/v2/pokemon-species`

The species listing is paginated and should be treated as returning:

- `count`
- `next`
- `previous`
- `results`

Each result contains:

- `name`
- `url`

The workflow should collect the first 40 species by following listing pagination.
Given the current upstream page size behavior, this means two listing pages of 20 items
each for a clean first run.

Each summary `url` points to a species detail record. The implementation should derive
the species id from that URL rather than trusting ordering alone.

## External data validation

The implementation must validate upstream data at the boundary before using it.

The species detail payload must validate the presence and shape of at least:

- `id`
- `name`
- `evolution_chain.url`
- `color.name`
- `color.url`
- `evolves_from_species` as nullable `{ name, url }`
- `generation.name`
- `generation.url`
- `habitat` as nullable `{ name, url }`
- `is_baby`
- `is_legendary`
- `is_mythical`
- `names[]` entries with `name` and `language`
- `genera[]` entries with `genus` and `language`
- `pokedex_numbers[]` entries with `entry_number` and `pokedex`

If upstream responses are malformed or unsuccessful, the seed operation must fail
clearly rather than silently continuing with partial or guessed data.

## Persisted data shape

The stored model should preserve the important species data needed for later reads while
remaining normalized enough for reliable querying.

### Parent species record

Each species record stores:

- `id`
- `name`
- `colorName`
- `evolvesFromSpeciesName`
- `generationName`
- `habitatName`
- `isBaby`
- `isLegendary`
- `isMythical`
- `seededAt`

### Localized names

Each localized name stores:

- `pokemonSpeciesId`
- `languageName`
- `name`

### Localized genera

Each localized genus stores:

- `pokemonSpeciesId`
- `languageName`
- `genus`

### Pokedex numbers

Each pokedex number stores:

- `pokemonSpeciesId`
- `pokedexName`
- `entryNumber`

## Representative expected values

The following representative values should be preserved by the workflow:

- species `1` is `bulbasaur`
- species `1` has `evolvesFromSpeciesName = null`
- species `1` has `colorName = green`
- species `1` has `generationName = generation-i`
- species `1` has `habitatName = grassland`
- species `2` has `evolvesFromSpeciesName = bulbasaur`
- species `3` has `evolvesFromSpeciesName = ivysaur`

## Database design requirements

The database layer should be shared and generic, not feature-specific.

That means:

- the seed feature should depend on an application-level database abstraction
- database configuration should use generic naming rather than seed-specific naming
- schema creation and migration should belong to the shared database layer
- local reset tooling must protect against deleting databases outside the repository or
  configured safe workspace

The plan does not require any specific ORM, migration tool, driver, or SQL library.
Those choices may change as long as the resulting behavior stays the same.

## Schema requirements

Use a normalized relational schema with:

- one parent table for Pokemon species
- one child table for localized species names
- one child table for localized genera
- one child table for pokedex number mappings

Required constraints:

- the parent species id is unique
- the parent species name is unique
- localized names are unique per `(pokemonSpeciesId, languageName)`
- localized genera are unique per `(pokemonSpeciesId, languageName)`
- pokedex numbers are unique per `(pokemonSpeciesId, pokedexName)`
- child rows reference the parent species row

Recommended indexes:

- species lookup by name
- child lookup by `pokemonSpeciesId`

## Seed algorithm

The seed operation should behave as follows:

1. Determine the longest contiguous seeded species prefix starting at id `1`.
2. If the contiguous prefix already reaches `40`, return a no-op result.
3. Start species listing discovery from the computed resume offset.
4. Continue through species listing pages until enough unique species summaries are
   collected to fill the missing portion of the `1..40` window.
5. Ignore species ids at or below the resume offset.
6. Ignore species ids above `40`.
7. Deduplicate candidate species ids during pagination.
8. Query the database for candidate ids that already exist.
9. Skip already stored ids before fetching species detail records.
10. If no species remain missing, return a no-op result.
11. Fetch detail payloads only for missing species ids.
12. Validate and normalize each detail payload.
13. Insert each species and its child records atomically.
14. Return the number of newly inserted species rows.

## Idempotency rules

The implementation must guarantee all of the following:

- rerunning the seed operation does not duplicate parent rows
- rerunning the seed operation does not duplicate child rows
- a fully seeded `1..40` dataset triggers no new upstream detail fetches
- existing noncontiguous rows are preserved and skipped rather than overwritten
- a species is either fully stored or not stored at all

The safest way to achieve this is:

- unique constraints on parent and child records
- transaction boundaries around parent-plus-child insertion
- existence checks before detail fetch and again at insert time when needed

## Execution surfaces

The feature should expose at least two ways to run the seed operation:

- an HTTP-triggered execution path such as `POST /seed/pokedex`
- a CLI-triggered execution path such as a project task or seed command

Both execution paths must use the same core seed service so behavior stays consistent.

## Tooling expectations

The repository should provide developer workflows for:

- running the seed operation
- generating schema migrations
- applying schema migrations
- checking migration history or consistency
- resetting the local database
- resetting and reseeding the local database

The exact command names can vary by language or toolchain. What matters is that these
workflows exist and are easy to run from the repository root or documented entrypoint.

## Testing requirements

Automated tests must cover:

- seeding from an empty database
- rerunning against a fully seeded database
- resuming from a partially seeded contiguous prefix
- preserving already stored noncontiguous ids
- failing clearly when the upstream species listing fetch fails
- HTTP-triggered execution success
- HTTP-triggered execution failure behavior

## Recommended test setup

Use a fresh temporary database for integration-style tests.

Tests should:

- apply migrations before running
- clear seeded tables between test cases
- replace the external fetch dependency with deterministic mocked responses
- verify database state directly after the seed operation

A good baseline test dataset is:

- species list pages that return predictable ids and URLs
- detail payloads that include one localized name, one localized genus, and one
  national pokedex number per species

## Required verification outcomes

After implementation, the following outcomes must be verified.

### First run

- the seed operation succeeds from an empty database
- exactly 40 parent species rows are stored
- the stored parent ids are exactly `1..40`

### Representative data

- species `1` stores `name=bulbasaur`
- species `1` stores `colorName=green`
- species `1` stores `generationName=generation-i`
- species `1` stores `habitatName=grassland`
- species `2` stores `evolvesFromSpeciesName=bulbasaur`
- species `3` stores `evolvesFromSpeciesName=ivysaur`
- child tables contain localized names
- child tables contain localized genera
- child tables contain pokedex numbers

### Rerun safety

- rerunning the seed operation succeeds
- rerunning after a full seed stores `0` new species
- rerunning does not increase parent row counts
- rerunning does not increase child row counts
- rerunning a fully seeded dataset performs no unnecessary upstream detail fetches

### Resume behavior

- if ids `1..18` exist and `19` is missing, the next run resumes from offset `18`
- if a later id such as `25` already exists, it is skipped instead of being fetched and
  inserted again
- after resume seeding, the total parent row count still reaches `40`

### Failure behavior

- if the upstream listing request fails, the seed operation fails clearly
- an upstream listing failure does not leave partially inserted parent rows for that run

## Duplicate-detection checks

The implementation should be verifiable with duplicate-detection queries equivalent to:

```sql
SELECT id, COUNT(*)
FROM pokemon_species
GROUP BY id
HAVING COUNT(*) > 1;
```

```sql
SELECT pokemon_species_id, language_name, COUNT(*)
FROM pokemon_species_names
GROUP BY pokemon_species_id, language_name
HAVING COUNT(*) > 1;
```

```sql
SELECT pokemon_species_id, language_name, COUNT(*)
FROM pokemon_species_genera
GROUP BY pokemon_species_id, language_name
HAVING COUNT(*) > 1;
```

```sql
SELECT pokemon_species_id, pokedex_name, COUNT(*)
FROM pokemon_species_pokedex_numbers
GROUP BY pokemon_species_id, pokedex_name
HAVING COUNT(*) > 1;
```

All of these queries should return zero rows.

## Regeneration checklist

To regenerate this feature in any stack:

1. Add a shared application-level database layer.
2. Introduce generic database configuration.
3. Define the normalized Pokedex schema and migration workflow.
4. Add a seed service that handles resume, fetch, validation, normalization, and
   persistence.
5. Add an HTTP-triggered entrypoint that delegates to the seed service.
6. Add a CLI-triggered entrypoint that delegates to the seed service.
7. Add local database reset and reseed workflows.
8. Add automated tests for success, rerun, resume, and failure behavior.
9. Verify the stored data and duplicate-protection guarantees.

## Historical note

An earlier version of the plan was too tied to one implementation approach. The merged
version intentionally avoids binding the feature to a specific commit, file layout,
language, ORM, or migration tool so future agents can reimplement it clearly in another
stack without mistaking implementation details for product requirements.
